# Atoolkit v9.3 迭代方案：多资产授权收口与运行环境路由

日期：2026-08-13
依据：gzfsf_172 工作区（QoderWork，Direct 模式）实跑反馈 + 只读审计（runs/gzfsf_20260813_blackbox）。

## 1. 背景与实证

v9.2 收口了报告出口（垃圾洞分层、代码渲染、hash 验真），但批量 Skill/Direct 实跑暴露出三个结构性问题，全部导致**真漏洞被误杀或流程被卡**：

### 问题 A：多资产/不同域名 finding 被 scope 误杀（实证）

`gzfsf_20260813_blackbox`：authz.md 授权 4 个资产（172.30.33.19:9001/:9003、172.30.34.94:8244/:8245），4 个 finding（OSS 凭证签发未授权、短信轰炸、用户枚举、验证码绕过）**全部 proof-rejected**，`accepted_findings: 0`。拒绝原因（state/checkpoint.json `rejected_items`）：

```
target out of authorized hosts: GET https://172.30.34.94:8244/rentingHouse/comprehensive/oss-sign
```

根因链（代码级）：

1. `skill_runtime init --target` 只接受单目标（skill_runtime.py:1352），ledger metadata 冻结单值 `target`；
2. `checkpoint_direct_run` 只拿这一个值当授权列表（skill_runtime.py:909-911 `authorized_hosts=[target]`）；
3. **authz.md 的 scope 列表没有任何代码消费**——它只是给模型看的散文。于是除主目标外所有授权资产上的 finding 全被拒。

派生资产第二层问题：OSS bucket（如 `*.aliyuncs.com`）由在册端点签发凭证，是攻击链合法一环，但 scope 模型没有"派生资产"概念；Engine manifest 模式下 proof packet 级校验（validate.py:1569 `_request_target_allowed`）会拦掉发往派生域名的证据包。

### 问题 B：授权文件多份重复维护 + 中途扩资产无通道（实证）

- 授权真相散落：QoderWork `AGENTS.local.md`（durable instructions）、ZCode 自有规则文件、每 Run 一份 `runs/<sid>/authz.md`——互相同步靠手工，内容漂移必然发生；
- installer 只装 AGENTS.md，IDE 适配文件全靠手写；
- scope 在 init 时冻结进 ledger，**无追加通道**：实跑中用户中途补加 8245 端口资产，唯一选择是重开 Run，否则新资产上的发现全被 checkpoint 拒掉。

### 问题 C：非 Codex 环境误调 codex/gpt-5.5（实证）

AGENTS.md 标题与开篇均为「Codex 运行约定（Codex 专用，置顶）」，且写「本文件同时服务 Engine Mode（run.py 驱动）」。`run.py` 真实运行路径默认 `--model gpt-5.5` 并实例化 `CodexAdapter`（run.py:1787、2426-2432）——QoderWork/ZCode 里的 agent 读到后尝试跑 `python3 run.py`，即拉起外部 codex/gpt-5.5 后端（计费与数据出站与当前 IDE 无关）。全文档没有一句「非 Codex 环境禁止 run.py」，run.py 自身也没有任何防护。

## 2. 设计原则

- 沿用 v9.2 原则：**边界由代码把守，不靠模型自觉**。scope 从散文升格为机器可消费的真相。
- 单一授权真相：workspace 级 `AUTHZ.md`（人维护一份）；各 IDE shim 只做指针；run 级 authz.md 可覆盖。
- 向后兼容：单 `--target` 调用方式不变；新参数全部可选；旧 run 目录无需迁移。
- 派生资产 ≠ 扩大攻击面：派生资产不能作为 finding 的 root target，只允许作为证据包目标，且必须声明签发来源。
- 不限制模型怎么测，只收"哪些目标的结果算数"这个口。

## 3. 修复设计

### 3.1 A：Direct 模式多资产 scope（根治项）

- `init`/`preflight` 新增：`--allow <url>`（可多次，命名对齐 run.py）与 `--scope-file <path>`（可多次）。`--target` 语义不变（主目标）。
- `--scope-file` 解析两种格式：
  - JSON（run_scope.json 等）：读 `target_domains` / `authorized_scopes` / `scopes` 列表，及 `derived_assets` 列表；
  - Markdown（AUTHZ.md / authz.md）：解析「授权 Scope」小节（匹配 `scope`/`范围` 标题）内列表行中的绝对 URL；「派生资产 / derived」小节同样解析。
- 全部条目经 `normalize_authorized_scopes` 归一化后写入 ledger metadata：`authorized_scopes: [...]`、`derived_assets: [...]`；`metadata.target` 保留主目标（向后兼容）。
- `checkpoint_direct_run` 与 guardian 校验改用完整 `authorized_scopes` 列表（缺省回退 `[target]`，旧 run 行为不变）。

### 3.2 B：scope 追加通道（`skill_runtime scope`）

- 新增子命令：`python3 -m engine.skill_runtime scope --run-dir <run> --add <url> [--add ...] [--derived <url>] [--reason <文本>]`。
- append-only：归一化、去重后并入 ledger metadata；审计行（时间戳/条目/reason）追加 `state/scope-audit.jsonl`；不写则已，写必留痕。
- 中途扩资产 = 跑一条 scope 命令后继续测，下一次 checkpoint 自然生效；不需要重开 Run。

### 3.3 C：派生资产（derived assets）

- 语义：由在册端点签发凭证/流程触达的第三方基础设施（OSS bucket、CDN、支付回调域）。**不得**作为 finding 的 target/apis（root 必须在册）；**允许**作为 proof packet / PoC 的请求目标，前提是 finding 声明 `verification.issued_by` = 签发凭证的在册端点 URL。
- validate.py：`validate_finding` 新增可选 `derived_hosts`；proof packet 目标不在册时，若命中 derived_hosts 且 `verification.issued_by` 在册 → 放行；否则维持拒绝。Engine manifest 模式：`ValidationContext` 从 manifest `derived_scopes` 读取；run.py 新增 `--allow-derived`（可多次）写入 manifest。
- Direct 模式说明：packet 级校验本就不启用（context=None），derived 主要约束 Engine 路径与语义表达；文档明确「往派生资产发包只能是为了验证在册端点签发的凭证/流程，且验证到足以证明即止」。

### 3.4 D：单一授权真相 + IDE shim 生成

- workspace 根新增 `AUTHZ.md`（installer 首次安装时生成模板，**已存在则不动**）：授权 scope 列表、派生资产、有效期、预授权动作、停手边界。这是唯一由人维护的授权文件；`init --scope-file AUTHZ.md` 消费它；run 级 `runs/<sid>/authz.md` 可从它复制并按 Run 收窄。
- installer 同步生成 `AGENTS.local.md` 薄 shim（已存在则不动）：只有「读 AGENTS.md + AUTHZ.md；scope 内动作已预授权；越界即停」数行，不含授权细节——QoderWork/ZCode/任意 IDE 通用，消除逐 IDE 重复维护。

### 3.5 E：运行环境路由（防误调 codex/gpt-5.5）

- 核心技能文件开头「运行约定」改为**运行环境路由**：
  - Codex CLI → 可用 Engine Mode（`run.py ... --via codex`）或 Direct 模式；
  - QoderWork / ZCode / 其他 IDE → **禁止 run.py Engine 路径**（会拉起外部 codex/gpt-5.5 后端）；只走 `skill_runtime` 六命令：preflight / init / observe / checkpoint / report / scope。
- run.py 硬防护：非 dry-run 的真实运行路径要求显式 `--via codex` 或环境变量 `ATOOLKIT_VIA=codex`，否则退出并打印路由提示。dry-run / audit / submission / score 不受影响（不实例化适配器）。
- AGENTS.md 标题去 Codex 中心化：「AI 辅助 SRC 漏洞挖掘运行约定」。

## 4. 影响面与兼容

| 变更 | 兼容 |
|---|---|
| init/preflight 新参数 | 可选，旧调用不变 |
| checkpoint 多 scope | 旧 run 无 `authorized_scopes` 时回退 `[target]`，行为不变 |
| scope 子命令 | 新增，无旧行为 |
| validate_finding `derived_hosts` | 可选参数，默认 None 行为不变 |
| run.py `--via` | **行为变化**：真实运行必须显式声明；dry-run 等不变。Engine 用户（Codex）需在命令加 `--via codex`，AGENTS.md 同步写明 |
| installer shim | 只新增不存在的文件，绝不覆盖 |

## 5. 验收标准

1. 四资产 scope 的 run 中，8244 上的 OSS finding 经 checkpoint 后不再因 scope 被拒（其余门正常判定）；复现 gzfsf 场景的多资产 fixture 测试通过。
2. `scope --add` 后新资产上的 finding 可 accepted；`state/scope-audit.jsonl` 有审计行；重复添加去重。
3. `--scope-file AUTHZ.md`（Markdown）与 run_scope.json（JSON）解析结果一致进入 metadata。
4. Engine manifest 模式：派生资产 packet 无 `issued_by` 仍拒；有在册 `issued_by` 放行。
5. `run.py --target ... `（无 --via、非 dry-run）退出码 2 且打印路由提示；`--dry-run` 不需要 --via。
6. 全新 workspace 跑 installer：AGENTS.md + AUTHZ.md 模板 + AGENTS.local.md 三件齐；二次运行不覆盖用户改动。
7. `pytest tests/ -q` 全绿；self-check 全过。

## 6. 实施结果（2026-08-13）

- 全部按 §3 落地：skill_runtime（多 scope/scope 子命令/scope 文件解析）、validate+collect（derived_hosts 链路 + ValidationContext.derived_scopes）、runtime_manifest（可选 derived_scopes，非身份字段）、orchestrator/run.py（`--allow-derived` 透传）、run.py `--via` 路由防护、installer（AUTHZ.md + AGENTS.local.md create-exclusive）、AGENTS.md 去 Codex 中心化。
- 测试：新增 `tests/test_v93_scope_routing.py` 9 例；`test_v89_run_cli_contract.py` 的 egress 用例补 `--via codex`（门顺序变化）。全套 451 passed / 1 skipped；self-check 30/30；doctor ok。
- **实跑回归（gzfsf_20260813_blackbox 原 run 目录）**：登记派生资产后重跑 checkpoint，此前被 scope 误杀的 4 个 finding（OSS 凭证签发未授权上传、短信轰炸、用户枚举、验证码绕过）全部 accepted、0 rejected；`report_ready=false` 维持正确（覆盖未闭合）。
- 备注：执行 `scope --add` 时发现 ledger metadata 已含全部 4 个在册资产（仅 OSS 派生资产为本次新加）——疑似仍有 live 的 QoderWork 会话写入了该字段，未能完全归因，但不影响结论：checkpoint 现在消费完整 scope 列表。
