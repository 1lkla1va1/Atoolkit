## 0. 审核结论先行：这版方案能解决什么、不能解决什么

### 能解决的（工程侧，确定性高）

| 问题 | 解法 | 解决机理 |
|---|---|---|
| 跨 Run 失忆：同一阻塞 6 周重复出现，每轮从零开始 | W1 | 机制代码已存在（Engine 侧有测试），Direct 从未接线；接线后每轮终态强制产出归因+agenda，下轮 init 强制消费 |
| NEED_INPUT 中途才暴露，跑到一半才发现缺账号 | W2 | 身份需求在首个网络动作前聚合成机器可读清单，阻塞前置 |
| 账号供给无台账：有什么账号、什么状态、缺什么，全靠散文 | W3 | 注册表把身份变成跨 Run 持久资产，需求自动带 registry_hint |
| 预算错配：身份不可达的 cell 与匿名可达的 cell 混排，预算被不可能完成的格吞噬 | W4 | 调度降权不可能完成的格，有限预算集中在可达格上 |
| 治理税：token 花在台账而非 HTTP 包 | W5 | 批量 observe + 增量 checkpoint |
| 产出打偏：P1 打到第三方仿冒站 | W6 | 提交出口机器校验目标 ∈ 官方 SRC 清单 |

### 不能解决的（必须对预期诚实）

1. **账号本身仍然要人提供。** W2/W3 把"缺账号"变成启动时的一张明确清单，但清单不会自己变出账号。若身份始终不到位，Run 的终态仍是 NEED_INPUT——区别只是：第一天就说清楚要什么，而不是第六周撞第四次墙。
2. **执行率上限受身份供给约束。** 若 60% 的格 identity_blocked，剩余可达格全部打满也只有 40%。因此 §3 的执行率指标是**条件指标**（分母排除 identity_blocked 格）。
3. **msToken/a_bogus 签名、真人核身等硬面不在本期范围**（行业公认残余瓶颈，见 §4）。
4. **不证明主站出洞能力。** v9.8 交付的是"当账号到位时，系统能把可达面打穿、把教训记住"。主站首洞仍需账号供给 + 实跑验证，这是 M1 验收之后的运营动作，不是本期代码的产物。

## 0.5 第一性原理复审（第二轮审核，2026-08-30）

复审方法：不问"机制是否接线、函数是否存在"，从唯一目标——**单位预算内产出可提交的真实漏洞**——倒推，逐条检验每个改动的因果链。本轮复审推翻了初稿的优先级排序。

### 复审发现 1（最重要）：真正的病灶是"冻结分母 ≫ 会话预算"的结构性失配，不是排序

吞吐恒等式：**闭合格数 = 会话预算 ÷ 单格成本**。feishu-scan 冻结 856 格、会话预算只跑出 9 个 event；arkbff 36 格跑出 7 个 event。分母比预算大两个数量级时，闭格门（§6：frozen scope 内有 not_tested 高价值格 → incomplete）**必然**输出 incomplete——这与执行质量无关，是设计在数学上的注定输出。W4 重排序只是把"完不成"重新排列，动不了这个恒等式。

→ **新增 W0（最高优先级）：预算匹配的分母冻结。** init 时按会话预算冻结 top-N 格（N = 可用预算 ÷ 单格成本估计，成本估计用 run.py 已有的 budget-dryrun 机制），其余 inventory 不进本轮分母、直接进入 agenda 预选池；closure gate 只对冻结子集求闭合。这与 v8.12 "禁止动态扩大分母"不冲突——它是**冻结得更小**，不是动态变更。M0 验收：重放 feishu-scan 的 init，冻结集 ≤ N 且闭合在数学上可达。

### 复审发现 2：历史上所有真洞都来自台账之外的自由探索，台账驱动的产出为零

磁盘事实：产出真洞的 Run（oss-dev-tos、volcengine-console-20260809）**根本没有 coverage-ledger**，目录结构只有 recon/evidence/findings；有完整台账的 Run 产出为零。也就是说被证据验证有效的回路是 **recon → 直觉假设 → 证明**，而 v9.8 初稿把全部投资押在从未产出过漏洞的台账回路上。

→ **修正：台账从"驱动器"降级为"记录器"，探索回路升格为一等公民。** 探索发现用最低成本落盘（W5 的批量 observe 优先服务这个）；覆盖闭合只约束 W0 冻结的小子集，不再对全攻击面求闭合。W4 只保留"exploring 信号正反馈"这一半（服务探索回路），全量 tractability 打分降级为条件项。

### 复审发现 3：W1 的因果链被高估，真正的关键路径在代码之外

"缺第二身份"6 周复现，不是因为散文记录丢了——操作者读到了记录，是账号从未被提供。失败点在**供给侧**，不在记忆侧。W1（机器化归因）是必要的卫生设施，但它不改变供给。第一性原理下，最高杠杆动作是**会话外的常驻账号矩阵**（一次性人工供给：实名火山账号×2、飞书第二租户、抖音账号B），它不是代码能交付的，但必须写进方案的关键路径——**账号矩阵到位前，带态面的预期产出为零，v9.8 任何工作流都不改变这一点。**

### 复审发现 4：W5 在优化一个从未被测量过的量

没有任何数据证明治理动作吃了多少预算——我们只观察到执行少，没测量过 token/时间花在哪。第一性原理：**先测量，后优化**。W5 第一步改为 instrumentation（orchestrator 相位打点 + observe/checkpoint 计时计数），用数据决定批量化/增量化的取舍，避免凭直觉优化。

### 复审发现 5：指标全是过程指标，且方案必须给出可证伪预测

执行率/复发率/接通率度量的是"忙不忙"，不是"出不出洞"。北极星改为**单位预算的可提交 finding 数**（允许滞后与噪声），过程指标降为诊断量。同时方案必须可证伪：**若"规划过剩+供给缺失"的诊断正确，M0+M1 完成后在匿名可达面续跑存量 Run，闭格率应从 ~1% 显著上升；若没有上升，说明诊断错误，停止 W3/W4，回头重查病因（候选：单格成本被低估、模型执行能力才是瓶颈）。**

### 修正后的优先级（取代 §1 表格的排序）

| 序 | 项 | 性质 | 为什么在这个位置 |
|---|---|---|---|
| 0 | **账号矩阵（人工）** | 方案外关键路径 | 供给侧唯一解，代码替代不了 |
| 1 | **W0 预算匹配分母** | 新机制 | 直接消除"0 闭格"的数学必然性 |
| 2 | W1 Direct 归因接线 | 接线 | 让 W0 的 agenda 预选池跨 Run 流转 |
| 3 | W2 身份需求前置 | 聚合 | 让"缺账号"第一天可见，服务第 0 项 |
| 4 | W5a instrumentation | 测量 | 后续一切优化的前提 |
| 5 | W4a exploring 正反馈 | 小机制 | 服务被验证有效的探索回路 |
| 6 | W6 提交归属校验 | 门禁 | 便宜且防真实损失 |
| 7 | W3 身份注册表 | 条件项 | 账号 ≤2 个时注册表是空系统，等账号矩阵 ≥5 个身份再建 |
| 8 | W4b 全量 tractability | 条件项 | W0 缩小分母后收益递减 |
| 9 | W5b 批量化/增量 checkpoint | 条件项 | 由 W5a 的测量数据决定做不做 |

## 1. 工作流总览与详细设计

## W0. 预算匹配的分母冻结（P0，第一性原理复审新增）

**目标**：让"闭格门在数学上可达"——冻结分母 ≤ 会话预算能覆盖的格数，消除"1007 格 0 闭合"的结构性必然。

### W0.1 单格成本估计与 N 的计算

- 成本数据源：run.py 已有的 budget-dryrun 机制 + 历史 Run 实测（当前唯一数据点：9-28 events/会话，即一个会话预算 ≈ 10-30 格。在 W5a instrumentation 落地前用这个保守区间，之后用实测均值）。
- `N = floor(可用预算 ÷ 单格成本估计)`，首版取保守值 N=20，配置化（`--max-frozen-cells`），不硬编码。

### W0.2 冻结与分流

- 切入点 `engine/skill_runtime.py:initialize_direct_run()` 与 Engine 侧 `planner.plan_surfaces()` 出口：surface 全量生成后，按既有优先级键（high_value → risk_tag 优先级 → 字典序，保持确定性）取 top-N 冻结进 coverage-ledger；其余进 `deferred-pool.json`（新产物：不记分母、不参与闭合判定，仅按优先级排序等待后续 Run）。
- `deferred-pool.json` 在终态时整体并入 `next-run-agenda.json`（W1 的 agenda 因此天然包含"本轮主动延后"项，cause_code 复用 `execution_not_started`）。
- **与 v8.12 的兼容性**：v8.12 禁止的是"运行中动态扩大 frozen denominator"；W0 是 init 期一次性冻结更小的集合，运行中不变——方向兼容。closure gate（validate.py `_run_closure_gate`）的判定对象不变，只是分母变小了。
- **防作弊闸**：N 不得为求闭合而恶意缩小——closure gate 增加一条：`deferred-pool` 中若存在 high_value 格而本轮执行率 < 80%（冻结格未打满就收尾），终态仍判 incomplete。这把"少冻结多闭合"的投机取巧堵死。

### W0.3 测试

- 同一 inventory 下 N=20 冻结集的确定性（两次 init 逐字节一致）；deferred-pool → agenda 的并入链路；防作弊闸：冻结格执行率 <80% 且 deferred 含高价值格时终态 ≠ complete。

## W1. Direct 归因/续航接线（P0）

**目标**：Direct 模式每个 Run 终态必产 `miss-attribution.json` + `next-run-agenda.json` + `finding_validation.json`；下一个 Direct Run 可用 `--continue-from-run` 消费。

### W1.1 checkpoint 复用 validate_run_artifacts，而非手写归因调用

**审核修订（重要）**：初稿设计是在 checkpoint 尾部手写调用 `build_miss_attribution` + 落盘两个 sidecar。逐函数审核后发现该设计会导致 W1.2 必然失败：

- `engine/continuation.py:load_prior_continuation()` 要求前一 Run 目录存在 `finding_validation.json`，且强制 `attribution == validation["miss_attribution"]`、`agenda == validation["next_run_agenda"]`、`verify_validation_artifact()` 通过（证据文件 artifact_hashes 逐一 sha256 复验）。
- 当前 Direct `checkpoint` 不产生 `finding_validation.json`（`skill_runtime.py` 中该词只出现在返回 dict 的摘要字段，非落盘文件）。
- 因此**唯一正确的接法**是复用现成入口：`engine/reporting/validate.py:validate_run_artifacts(run_dir, allowed_hosts=..., write_sidecars=True)`——它内部已构建归因+agenda、嵌入 validation 输出、落盘 sidecar（:3870-3891），且已被 Direct 的 `report` 命令使用，证明 Direct-safe（Direct 无 authority manifest 时该校验路径自动跳过 authority 绑定段）。

**实施**：
- 切入点 `engine/skill_runtime.py:checkpoint_direct_run()`，在现有收敛与 projection 重算完成、status 组装之后，调用 `validate_run_artifacts(...)` 输出到 `<run>/finding_validation.json`，sidecar 随之落盘。
- checkpoint 返回值新增 `attribution_summary`（cause_code 分布、agenda 条数、identity_missing 计数），供会话直接引用。
- **禁止**在 Direct 侧另造归因格式或绕过 validate_run_artifacts 手写 sidecar——continuation 的三重一致性校验（attribution↔validation↔确定性重放）会拒绝任何分叉格式。
- 性能注意：validate_run_artifacts 会重新收集 findings，与 checkpoint 已有收敛存在重复计算。本期接受该成本（正确性优先），W5 再统一做增量化。

### W1.2 init 增加续跑入口

- `engine/skill_runtime.py:initialize_direct_run()` 增加 `--continue-from-run <run-dir>` 参数，调 `engine/continuation.py:load_prior_continuation(prior_run, primary_target=..., authorized_scopes=...)`。
- 注意 loader 的两个硬约束，init 必须满足：① agenda item 的 endpoint 若含完整 URL，必须命中本轮 `--allow` scope（`is_authorized_url`），否则 ContinuationError；② prior run 的证据文件在 continuation 时必须仍在原位（artifact_hashes 复验）——**文档中须明示：续跑前不得清理/移动上一 Run 目录**。
- continuation items 并入 inventory rows（`_merge_rows` 之前），`continuation-input.json` 落盘绑定本轮 run_dir；只恢复调度，不改 ProjectState，不提升 submission eligibility（Direct 恒 diagnostic）。

### W1.3 测试

- `tests/test_v98_direct_attribution.py`：构造含 blocked/shallow_negative/未闭合格的 mock Direct run → checkpoint → 断言三件套落盘、`load_prior_continuation` 能直接消费该目录（round-trip 是真验收）、digest 篡改时被 ContinuationError 拒绝。
- 存量重放验收：对 byteDance `runs/feishu-scan`（856 格）重跑 checkpoint，断言每个 in-scope 格恰好一个 cause_code。

## W2. 身份需求前置申报（P0）

**目标**：首个网络动作前输出 `<run>/identity-requirements.json`，把"缺什么身份、缺几个、卡住哪些格、请人工做什么"写成机器可读清单。

### W2.1 Engine 路径（threat mode）

- 数据源现成：`engine/engine_planning.py:build_identity_readiness()` 按 threat 的 `identity_requirement.mode`（peer_pair / role_pair / anonymous_plus_authenticated / stateful_owner）评估，reason_code 四档（distinct_identity_missing / peer_role_pair_missing / required_role_pair_missing / test_owned_object_missing）。
- 切入点：`run.py` 在 readiness 计算之后、首个网络动作之前，物化 `identity-requirements.json`（schema 见下），并在 stdout 输出人类可读摘要。

### W2.2 Direct 路径（legacy_risk，无 threat model）——审核修订

初稿假设 Direct 也能复用 readiness 输出。**审核发现：Direct legacy 模式没有 threat-model.json，`build_identity_readiness()` 遍历 `threat_model["features"][*]["threats"]`，空输入即空输出**——Direct 下该函数无事可评。因此 W2 必须新增一个 Direct 侧启发式推导器（建议 `engine/identity_requirements.py`，Engine/Direct 共用出口）：

- 输入：init 后的 inventory rows + coverage-ledger surfaces。
- 推导规则（确定性、可测试）：risk_tag 含 `idor`/对象参数对 → `peer_pair, minimum=2`；含 `admin`/`privilege` → `role_pair`（required_roles 取 inventory 中出现的角色集）；含 `txn`/`amount` → `stateful_owner`（需 owned object）；匿名可达面 → `single`。
- 推导结果与 Engine 路径汇合到同一个 `identity-requirements.json` schema：
  ```json
  {"schema_version": "1",
   "requirements": [{"requirement_id": "req-001", "mode": "peer_pair",
     "reason_code": "peer_role_pair_missing", "role": "tenant_user",
     "count_needed": 2, "count_present": 1,
     "blocks_cells": ["surface_id 列表"],
     "human_action": "提供第二个飞书租户成员账号（登录态 cookie 或测试账号）"}],
   "summary": {"total_requirements": 0, "blocked_high_value_cells": 0}}
  ```
- 降级不阻塞：缺口 cell 标 `identity_blocked=true` 留在队列（供 W4 降权），本轮其余 cell 照常。
- checkpoint 时复算 requirements 并比对：仍缺 → 这些 cell 的 `cause_code=identity_missing` 自动进入归因（与 W1 闭环）。

### W2.3 测试

- 推导器规则逐条单测（每种 risk_tag → 预期 mode/minimum）；`blocks_cells` 与 ledger 交叉引用一致性；补 identity 后重算缺口清零的回归。

## W3. 身份注册表（P1）

**目标**：账号/凭据成为跨 Run 持久资产。

### W3.1 新模块 `engine/identity_registry.py`

- 落盘 `<project>/identity-registry.json`（fcntl 锁 + schema 版本化，仿 `project_state.py` 的 store 模式）：
  ```json
  {"schema_version": "1",
   "identities": [{"label": "volc-user-a", "kind": "web_session|api_key|account",
     "role": "tenant_user", "target_scope": ["*.volcengine.com"],
     "credential_sha256": "...",
     "credential_ref": "runs/volcengine-apigw_20260830/identities.json#a",
     "source": "user_provided|self_registered",
     "created_at": "...", "last_verified_at": "...",
     "status": "active|expired|mfa_required|unverified",
     "notes": "已实名/MFA 尾号95"}]}
  ```
- **审核修订——credential_ref 是必须字段**：初稿只存指纹，审核发现这会使注册表无法支撑"复用"（指纹不能发包）。注册表必须记录凭据本体的位置指针（run 内 identities.json 的 label 锚点，或项目级安全凭据目录，复用现有 `.authority/` 的权限收紧写盘约定）。红线不变：**注册表本身不存明文凭据**；凭据本体仍在权限收紧文件里。
- 指纹归并复用 `run_authority.canonical_credential_sha256`。

### W3.2 写入路径（三条）

1. `run.py` 的 `--identity` 解析段改为 registry-aware（入册/更新 last_seen）。
2. `skill_runtime.observe` 的 outcome 集合新增 `created_account`（结构化字段：label/role/target_scope/credential_ref）——把 v9.5「数据即写」散文纪律升级为机器事件，自助注册账号自动入册。
3. barrier_signals 触发状态迁移（session_expired → status=expired 等）。

### W3.3 消费路径

- W2 的 requirements 增加 `registry_hint`：如"注册表中有 1 个匹配身份但 status=expired，credential_ref=...，请刷新登录态"。
- init 时列出 target_scope 匹配的可用身份清单（label + status，不显示凭据），由操作者决定是否通过 `--identity` 注入——**不自动读凭据本体**。

### W3.4 测试

- CRUD + 指纹归并 + 锁并发；created_account → 入册链路；expired 不进 readiness；credential_ref 悬空了（源 run 被清理）时的降级行为（标 status=unknown，不崩）。

## W4. 调度改进（复审后拆分为 W4a 本期 / W4b 条件项）

**复审修订**：W0 缩小分母后，全量 tractability 打分的边际收益大幅递减（队列里本来就不再有大量不可能完成的格）。本期只做服务探索回路的一半。

### W4a（本期）：exploring 信号正反馈

- observation 出现 response differential（`outcome=exploring` + 有效 evidence_refs）时，同 surface 族的兄弟 cell 在 `CoverageLedger.next_surfaces()` 与同 queue sort 中升权——「有微弱信号继续追」的机器化。
